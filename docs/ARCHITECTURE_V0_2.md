# Архитектурный манифест и устройство ядра Astrosite v1.0.1

## 1. Концепция и фундаментальные догмы

1. **Неприкосновенность ядра:** Никакие изменения файлов задач (манифесты, генераторы, виджеты, разметка) не требуют пересборки контейнеров (`pnpm build`, `docker compose build`) или перезапуска демона ядра[cite: 5]. Директория задач вынесена на внешний Docker Volume (`./data/tasks:/app/data/tasks`)[cite: 5].
2. **Принцип «песчаного замка» (Graceful Degradation):** Поломка отдельной задачи (синтаксическая ошибка в Python, невалидный JSON, сбой генерации) полностью изолируется на уровне сканера[cite: 5]. Сервер логирует инцидент, исключает сломанную задачу из публичного каталога и возвращает `422 Unprocessable Entity` только для текущего проблемного запроса[cite: 5]. Падение сервиса (HTTP 500) исключено[cite: 5].
3. **Изоляция исполнения интерфейса (Iframe Sandbox):** Каждый интерактивный тренажёр отображается в песочнице `<iframe>`[cite: 5]. Любые ошибки в JavaScript-коде задачи не затрагивают основное React-приложение и не вызывают «белый экран»[cite: 5].
4. **Анонимность и отсутствие ПДн:** В системе отсутствуют формы регистрации, пароли и сбор персональных данных[cite: 5]. Идентификация построена вокруг 128-битных псевдослучайных токенов в `HttpOnly`-cookie[cite: 5]. Ключ служит открытым кодом сессии, который ученик прикрепляет в электронный журнал для отчётности[cite: 5].
5. **Аудит действий (Append-Only Event Stream):** Все действия пользователя (подбор коэффициентов, клики, наведение, изменение ответов) пачками отправляются в таблицу `events`[cite: 5].
6. **Персистентность и долгоживущие сессии:** Пока работа не сдана (`submitted_at IS NULL`), повторные переходы пользователя по ссылке задачи или обновление страницы возвращают существующую попытку с теми же сгенерированными данными и восстановленным черновиком ответов.

## 3. Модель данных (PostgreSQL)

База данных работает в схеме `astrosite_v2` и автоматически инициализирует таблицы при старте:

* `users`: хранит хеш ключа (`key_hash`) для внутренней проверки и открытый токен (`raw_key`) для сопоставления с электронным дневником.


* `attempts`: сохраняет привязку к пользователю (`user_id`), идентификатор задачи (`task_id`), `seed`, полный снимок сгенерированного варианта (`task_data`), сданные или промежуточные ответы (`answers`) и отметку сдачи (`submitted_at`).


* `events`: хронологический журнал действий с фиксацией имени события, JSON-полезной нагрузки и серверного времени.



### Жизненный цикл попытки (Attempt Lifecycle)

1. **Создание / Получение:** Запрос `POST /api/attempts` ищет незавершённую попытку текущего пользователя по задаче. Если найдена — возвращается она. Если сдана или отсутствует — создаётся новая строка.
2. **Промежуточное сохранение:** При изменении состояния в виджете родительский контейнер отправляет `PATCH /api/attempts/{id}/answers`, сохраняя черновик в колонку `answers`.
3. **Сдача:** Инициируется виджетом (`ASTROSITE_SUBMIT_ATTEMPT`) или внешней кнопкой через `POST /api/attempts/{id}/submit`. Выставляется `submitted_at = NOW()`, попытка блокируется от дальнейших изменений.
